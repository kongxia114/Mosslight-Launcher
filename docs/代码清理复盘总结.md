## 二、清理原则（下次照这个来）

| # | 原则 | 具体做法 |
|---|---|---|
| 1 | **先确认，后动手** | 先出「删除清单 + 证据链」，经确认后才落盘；不确定的一律标注「需人工确认」 |
| 2 | **一次一个文件** | 每轮只动一个文件；跨文件的连带调整单独列项、单独请示 |
| 3 | **证据链三件套** | ① 全仓符号引用计数（`.cs` + `.xaml` + `.md`）② 事件绑定/反射/字符串调用的交叉检索 ③ 构建验证 |
| 4 | **护身符不动** | 解释「为什么」的注释、踩坑记录、兼容性/状态机/正则说明，一字不改（含标点） |
| 5 | **零行为变化** | 只删「删掉以后行为完全不变」的东西；语义不明即视为不可删 |
| 6 | **零格式化漂移** | 不重排、不重命名、不改引号/缩进/空行风格，不「顺手优化」 |
| 7 | **删除可追溯** | 交付 `git diff` 或逐段比对结果；每一行删除都能对上清单编号 |
| 8 | **移葬优先于陪葬** | 死代码里夹着的历史经验，迁到替代实现的注释旁，而不是跟着一起删 |

> 一句话版本：**删的是「没人用」，保的是「为什么」，绝不碰「怎么写」之外的任何东西。**

## 四、判定标准与误报案例（重要）

### 4.1 判定模板

```
删除前必须能回答：
1. 这个符号在全仓（.cs / .xaml / .md）出现过几次？>1 且不是「被自己调用」→ 不删
2. 有没有可能被事件绑定（XAML 特性）、反射、字符串拼接、序列化按名调用？→ 有 → 不删
3. 删掉后行为是否 100% 不变？→ 不确定 → 不删，标「需人工确认」
4. 它旁边的注释是 What 还是 Why？→ Why → 先迁移，再删
```

### 4.2 本轮踩过的误报（教训）

| 误报 | 为什么是误报 | 教训 |
|---|---|---|
| `MemoryBar.MeasureOverride` | 引用计数为 1，但它是 WPF 框架回调（重写） | 私有扫描必须排除 `override` / 接口实现 |
| `NavIcons.cs` 的 `System.Windows.Shapes` | 用到了 `Path` 类型，但 `Path` 与 `System.IO.Path` 同名 | using 检查要覆盖**短类型名易混淆**的命名空间 |
| `VersionIcons.ChipSize`、`DownloadManager.StateWaiting` 等 | 引用为 0，但属公开 API / 与在用常量成对 | 公开 API 不按「零引用」处理，按产品决策处理 |
| `AboutDialog` 的 `else` 分支 | 常量非空导致不可达，但删它会让 5 个语言文件的 key 变孤儿 | 删 UI 文案前先查语言文件 |

> **误报的成本远高于漏报**：漏一条下次还能补；误删一条可能就是线上事故。

## 五、护身符清单（禁止清理）

以下注释**不解释「代码在做什么」，而解释「为什么只能这么写」**。
它们通常以 `⚠️` 开头，删除前必须获得业务方确认。

| 主题 | 位置（符号） | 教训摘要 |
|---|---|---|
| 双流下载进度 | `DownloadTask.ReportBytes` | 两条流**不能累加**，取最大，否则进度条跑到 200% |
| 取消令牌复用 | `DownloadTask.PrepareRetry` | `CancellationTokenSource` 取消后永久失效，重试必须换新对象 |
| 下载状态机 | `LoadingBar` 的 `_hideDoneTimer` | 「该收起了」不能挂在 `animation.Completed` 上（实测不触发），要挂定时器 |
| 加载条防抖 | `LoadingBar` 的 `_generation` | 延迟收起必须核对「显示代数」，且**无论是否匹配都要放掉 `_hiding`**，否则永久转圈 |
| 滚动续取阈值 | 原 `OnDetailScrollChanged` → 已迁至 `ApplyDetailGroups` 上方 | 阈值 160 的提前量；只认竖向变化，否则铺行过程中反复触发 |
| 异常类型顺序 | `DownloadManager.ShortError` | `TaskCanceledException` 必须排在 `OperationCanceledException` **前面**（子类） |
| 语言切换 | `PersonalizePage` 类注释 / `MainWindow.ApplyLanguage` | 已建控件的 `{loc:Tr}` 不会重算，必须整页重建 |
| JSON 读取 | `JsonIO` 类注释 | `JsonNode.Parse` 不认 BOM，记事本存过的版本 JSON 会「消失」 |
| 镜像映射 | `DownloadManager.MirrorUrl` / 文件头 | 每条映射必须实测，猜错不崩但会白等超时 |
| 图标缩放 | `VersionIcons.ScaleToLongest` | 256→28 一次缩会糊，必须分步；按 DPI 算目标物理像素 |
| 加载器识别 | `ModsDirectory` 文件头 | 不能用「包含」匹配（forge 会命中 neoforge），必须整体比对 |
| 兜底地址 | `DownloadTask` 构造 | 安装器 jar 只有一个源，镜像 403 时整条安装失败，所以要有备用地址链 |

> **防呆约定**：清理工具/脚本在处理注释时，**默认跳过含 `⚠️` 的行及其紧随的续行**。

## 六、护身符防呆建议（机制化，而不是靠自觉）

### 6.1 编译期 / CI 门禁

| 建议 | 做法 | 收益 |
|---|---|---|
| 零警告基线 | CI 里 `dotnet build -warnaserror`（或至少把新增警告视为失败） | 本仓现在就是 0 警告，别让它退化 |
| 未使用 using | 启用分析器 `IDE0005`（`dotnet_diagnostic.IDE0005.severity = warning`） | 自动拦住本轮手工发现的 6 处同类问题 |
| 未使用私有成员 | 启用 `IDE0051`（未使用私有成员）、`IDE0052`（只写不读私有成员） | 自动拦住 `ShowAnimMs` / `ConnectTimeout` 这类「编译器不报」的死常量 |
| 未读参数 | 启用 `IDE0060` | 顺手清理签名遗留 |
| 验证门禁可用性 | `dotnet format analyzers --verify-no-changes` | 让上面几条在 CI 里真正生效而非仅提示 |

> 注意：`const` 未使用**不会**触发编译器警告，`IDE0051` 是目前最可靠的一道网。

### 6.2 文档引用防呆

- 现在 `.csproj` 未开启 `<GenerateDocumentationFile>`，所以 `<see cref="已删符号"/>` **不会报警**。
  本轮 `PersonalizePage` 就出现了一处失效 `cref`（已修正为 `MainWindow.ApplyLanguage`）。
- 建议二选一：
  1. 开启 `<GenerateDocumentationFile>true</GenerateDocumentationFile>`，让 `CS1574`（失效 cref）成为警告；
  2. 或在 CI 加一条脚本：抽取 `docs/design-notes.md` 与源码注释里的 `<see cref="X"/>`，逐个 grep 是否存在。

### 6.3 XAML 孤儿元素防呆

本轮删掉了一个「永远不会显示」的 `TextBlock`（`NotMigratedText`：唯一的写入点已死，且默认 `Collapsed`）。

- 建议脚本：对每个 `.xaml` 提取 `x:Name`，若在全部 `.cs` 中零引用、且本文件内也无 `ElementName`/`TargetName` 引用 → 报告。
- 注意：`x:Name` 也可能纯为可读性保留，这类检查只作**提示**，不自动删。

### 6.4 重复常量防呆

本仓存在一处已知重复：`AppInfo.RepoUrl`（public，零引用）与 `AboutDialog.ProjectUrl`（private，在用）**指向同一个仓库地址**。
按「保持 API 族群完整」的决策，本轮保留，但建议后续：

- 要么让 `AboutDialog` 改用 `AppInfo.RepoUrl`（单一真相）；
- 要么在 `AppInfo` 里删掉 `RepoUrl`（API 收缩）。

同类风险：状态字符串 `DownloadManager.StateXxx` 与 `DownloadState.Xxx` 是两套入口 —— 保留是产品决策，但**新增状态时两边都要改**，需要在注释或自检里明确这一点。

### 6.5 语言 key 防呆

删除界面上的一句文案前，先确认对应 key 是否还被其它地方使用：

- 本仓的 `tools/check_lang_keys.py`（语言键完整性检查）目前处于**未暂存删除**状态（工作区迁移，见第八节）。
- 建议该门禁在 CI 中保留，避免「删一句文案 → 5 个语言文件留下孤儿 key」或反过来「新增文案忘补翻译」。

### 6.6 约定层

1. **历史经验统一前缀**：本轮迁葬时使用了 `// ── 历史踩坑记录：…`，便于 grep 与后续迁移。
2. **护身符标记**：全仓已基本统一用 `⚠️` 开头，建议在贡献指南里写明「清理时跳过 ⚠️ 段」。
3. **删除公开符号前必须全仓 grep**（`.cs` + `.xaml` + `.md`），因为 `cref`、XAML 绑定、反射都可能是隐蔽引用。
4. **一个清理主题一个 commit**：提交信息写清「删了什么 / 为什么安全」，便于 review 与回滚。

### 6.7 流程层

1. 清理前确认工作区状态（未提交的他人改动不要一起裹进提交）。
2. 每轮改动前后各跑一次构建；有条件时跑自检（`Mosslight.Core.SelfCheck`）。
3. 删除后做**逐段比对**（改动前后行数组对齐），证明「只有清单里的位置变了」。
4. 有历史价值的注释优先**移葬**，而不是随死代码一起消失。

## 九、给未来的清理者（TL;DR）

1. **先证明它是死的**（引用计数 + 绑定/反射排查 + 构建），再动手。
2. **一次一个文件**，跨文件改动单独请示。
3. **注释先看是 What 还是 Why**：Why 的，迁移；What 的，随代码删。
4. **不确定就不删**，标「需人工确认」不丢人。
5. **删完要能证明「只有这里变了」**：diff + 构建 + 逐段比对。
6. **别顺手**：不重排、不重命名、不格式化、不「优化」。
