# 1.0.0 → 2.0 风格对照表

这份文档回答一个问题：**「照搬 1.0.0 的风格」具体是怎么搬的？**

2.0 是 C# / WPF 重写版，1.0.0 是 Python / PyQt6。两边的样式机制完全不同
（QSS 是文本样式表，WPF 是资源字典 + 样式对象），所以"照搬"不是复制粘贴，
而是**一条一条映射**。这里记的就是那个映射关系，以及**哪些地方不可能一样**。

源（1.0.0，权威）：`D:\开发工程\DHML-src`
目标（2.0）：本目录（`D:\开发工程\Mosslight-Launcher 2.0\Mosslight-Launcher 2.0\`）

---

## 1. 颜色：48 个 token，**生成的**，不是手抄的

1.0.0 的颜色全在 `core/theme.py` 的 `DARK` / `LIGHT` 两个字典里（各 48 个），
QSS 里的 `@bg_card@` 这种占位符由它替换。

WPF 这边要的是一份 `ResourceDictionary`，所以：

```
python D:\deepseek\.dhml-tests\gen_theme_xaml.py
```

这个脚本从 `core/theme.py` 生成三个文件：

| 生成物 | 用途 |
| --- | --- |
| `Mosslight.App\Themes\Theme.Dark.xaml` | 深色主题字典（48 个 `Color` + 48 个 `SolidColorBrush`） |
| `Mosslight.App\Themes\Theme.Light.xaml` | 浅色主题字典（同上） |
| `Mosslight.Core\Theme\ThemeData.g.cs` | 同样 48 个值的 C# 常量，给运行时算强调色用 |

**键名规则**：`bg_card` → `BgCard`（`Color`）+ `BgCardBrush`（`SolidColorBrush`）。

> ⚠️ **为什么用生成的**
> 手抄一份 48 个值的表，迟早会飘（那边加了个 token、这边忘了）。
> 生成之后"改配色"只有一个动作：改 `theme.py`，重新生成。
> 生成的文件头都写着"别手改"。

### 强调色那一族（14 个键）是运行时算的

用户可以自定义强调色（个性化页那些圆点），这时要派生出一整族：
`accent` `accent_fill` `accent_fill_hover` `accent_fill_pressed` `accent_text`
`accent_text_strong` `accent_bg` `accent_border` `accent_bg_disabled`
`accent_border_disabled` `accent_text_disabled` `accent_selected_bg` `avatar_bg` `on_accent`。

**算法逐字移植**在 `Mosslight.Core\Theme\ColorMath.cs` + `ThemeService.cs`：

| Python (`core/theme.py`) | C# | 坑 |
| --- | --- | --- |
| `_to_rgb` | `ColorMath.ToRgb` | 分量除以 255 |
| `_to_hex` | `ColorMath.ToHex` | **先 `round` 再钳**；`round()` 是银行家舍入 → `Math.Round(x, MidpointRounding.ToEven)` |
| `shift` | `ColorMath.Shift` | HLS 公式照 `colorsys` 抄，不能"用 HSL 差不多" |
| `blend` | `ColorMath.Blend` | 参数顺序是 `(fg, bg, ratio)` |
| `readable_on` | `ColorMath.ReadableOn` | BT.601 亮度 > 0.62 → `#101317`，否则白 |
| `effective_mode` | `ThemeService.EffectiveMode` | `system` 落到实处的 dark/light |

派生系数是**照抄**的，例如 `accent_fill = shift(accent, -0.13)`（深色）/
`-0.06`（浅色）。**别"顺手调好看一点"** —— 调了两个版本的同一个主题色就不是一个观感了。

**验证**：`Mosslight.Core.SelfCheck` 会拿 Python 算出来的金标准
（`tests\theme_golden.json`，2 套主题 × 7 种强调色 × 48 个 token = 672 个值）
逐值比对，差 1 就红。金标准由 `gen_theme_golden.py` 生成。

## 2. 卡片透明度 & 外壳半透明

1.0.0 在 `ui/widgets/card_style.py` 里做两件事，WPF 这边对应
`Infrastructure\ThemeApplier.cs` 的 `ApplyCardOpacity` / `ApplyChrome`：

| 1.0.0 | 2.0 | 说明 |
| --- | --- | --- |
| 卡片底色 alpha = `round(opacity/100*255)` | `CardSurfaceBrush` | 只作用于**卡片**（`#Card`/`#AccountChip`/`#ModCard`…），**按钮、输入框、滚动条不跟着透明** |
| 卡片描边同样 alpha | `CardBorderBrush` | |
| 悬停底色 `bg_elevated` 同样 alpha | `CardHoverBrush` | 对应 `HOVER_SELECTORS` |
| 侧边栏固定 `0.82` alpha，**只在设了背景图时** | `SidebarBrush` | 没设图时把侧栏弄透只会跟页面糊成一片 |

> ⚠️ 卡片底色**不能**复用 `BgCardBrush`：那个键还被侧边栏悬停、档案卡片用着，
> 一起变透明会把那些地方也弄花。所以单独四个键。

## 3. 背景图：五种铺法

命名和顺序**对齐 Windows 的"选择适合度"**（这样用户不用重新学一套说法）。
1.0.0 在 `ui/widgets/background_canvas.py` 里用 `QPainter` 手画，
WPF 这边用 `Image` 的 `Stretch` + 对齐方式（`Infrastructure\BackgroundHost.cs`）：

| 铺法 | PyQt6 | WPF |
| --- | --- | --- |
| 填充 `fill` | `KeepAspectRatioByExpanding` + 居中 | `Stretch=UniformToFill` + 居中 |
| 适应 `fit` | `KeepAspectRatio` | `Stretch=Uniform` |
| 拉伸 `stretch` | 直接缩放 | `Stretch=Fill` |
| 居中 `center` | 原图大小居中 | `Stretch=None` + 居中 |
| 跨区 `span` | 铺满宽、纵向居中裁切 | `Stretch=UniformToFill` + 居中 |

**压暗**：1.0.0 里 `dim`（0~200）是**直接当 alpha 用**的（不是百分比），
而且**只在对有图时生效**。WPF 照做。

**纯色背景**只在没有图的时候才画（1.0.0 的注释：「纯色才生效」）。

**窗口那层底色必须不透明**（`BgPageBrush`）：选「居中 / 适应」时图以外的地方
画布是不画的，露出来的就是窗口底色 —— 露成黑色或者穿到桌面都很难看。

## 5. 动效

预设表在 `core/anim_prefs.py`（7 档风格 × 5 档速度），2.0 逐字移植到
`Mosslight.Core\Animation\AnimationPresets.cs`：

| 概念 | Python | C# |
| --- | --- | --- |
| 预设 | `PRESETS[key]`（`AnimationPreset` dataclass） | `AnimationPresets.Presets[key]` |
| 认不出来 | `PRESETS.get(key) or 默认` | `Preset(key)`（不抛异常） |
| 速度档 | `SPEEDS`（倍率，中英混排的显示名） | `Speeds` / `SpeedFactor` |
| 缩放 | `scaled()`：duration×f、interval×f，各自有下限 | `Scaled()`，下限 40ms / 8ms |
| 版本列表用短参数 | `preset_for_versions()` | `ForVersions()` |
| 淡入占整条轨迹的比例 | 无（非 PCL 形态根本不淡入） | `AnimationPreset.FadeRatio`（**新增**） |

> ⚠️ **这张表对的是"概念"，不是"数值"**：上面七档的**时长 / 位移 / 错峰 / 缓动 / 过冲**
> 是**重新调过的**，跟 `anim_prefs.py` 里的原值不一样（用户对 1.0.0 那套手感的评价是
> "太鸡肋"）。1.0.0 的原值仍然能从 `tests/slide_anim_golden.json` 里读到，
> 那一节验的是**轨迹引擎**跟 Python 逐值一致（用的是金标准里的参数，跟预设表无关），
> 所以"逐值对齐"这件事照样可验。调参依据见 `AnimationPresets.Presets` 的注释。

**缓动曲线**：1.0.0 有自己实现的参数化版本（`ui/widgets/pcl_ease.py`，
因为 Qt 内置的 OutBack 过冲写死 10%），WPF 自带的那几个**表达不了**，
所以是**照公式重写**（`Infrastructure\ParametricEase.cs` + `EasingFactory.cs`）：

| 1.0.0 | 2.0 |
| --- | --- |
| `cubic` | WPF 自带 `CubicEase` + `EaseOut` |
| `quint` | WPF 自带 `QuinticEase` + `EaseOut` |
| `inout` | WPF 自带 `CubicEase` + `EaseInOut` |
| `back:0.10` | `ParametricBackEase`（自实现，峰值过冲 10.00%） |
| `elastic` | `ParametricElasticEase`（自实现，峰值 1.371015） |
| `spring:0.xx` | `ParametricDampedSineEase`（自实现，**过冲只有设定值的 13%**，见下面那条） |

> ⚠️ **踩过的一个坑（值得记住）**：WPF 的 `EasingFunctionBase.Ease()` 会**再加工一次**
> `EaseInCore` —— `EaseOut` 时是 `Ease(t) = 1 - EaseInCore(1-t)`。
> 把 Python 的缓出公式直接塞进 `EaseInCore` 会得到 `1-f(1-t)`：曲线左右镜像再上下翻转，
> **形状完全变了，但编译能过、动画看着也"挺顺"**。只有逐值比对抓得住。
> 所以有个 `PythonOutEase` 基类统一做反演 `EaseInCore(u) = 1 - f(1-u)`，
> 子类只管照抄 Python 的 `f`；自检里还有一条断言专门盯着这个约定本身。

> ⚠️ **`spring:0.xx` 的那个数不是过冲百分比**：实测峰值过冲只有设定值的 **13%**
> （填 0.14 量出来约 1.6%）。
> 根因在 Python 自己身上 —— `make_damped_sine` 按"未经 `shaped` 整形的包络峰值"
> 归一化，而实际曲线走的是整形后的时间轴。所以它只是个**相对**系数（越大越弹）。
> 我们**照抄了这个行为**（观感一致优先），没有"顺手修正"。
> 要让它真的等于 14% 过冲，那是对 1.0.0 的行为改动，得单独决策。
>
> ⚠️ **这一条在调参时咬过一次**：一开始把「弹性」那档的主段缓动从 `elastic` 换成
> `spring:0.12`，想着"过冲比例能照着填更可控"——量出来过冲只有 **1.6%**（等于没有回弹）。
> 所以那档最后**保持 `elastic` 不变**，改的是时长和位移；
> 「弹簧」那档的"弹"来自 `AnimationStyle.Spring` 自己的 `SpringBump`
> （那条**过冲严格等于 `OvershootPx`**，没有这层归一化问题）。详见
> `AnimationPresets` 里那两个常量的注释。

**动效挂在哪**：1.0.0 里 `slide_in` 只用在**版本列表**（`collapsible_group.py`）
和**模组页的两个列表**（`mods_page.py`）上；`home_page.py` / `personalize_page.py`
是普通卡片直接进布局，**一帧动画都没有**。所以 2.0 的这两页 `AnimationHost` 返回 `null`
—— 这是**照搬**，不是"为了截图好看"的将就。

**总开关**：1.0.0 关掉动效时列表**根本不包那层动画控件**（不是"时长为 0"）。
WPF 这边 `PageAnimator.AnimateIn` 在总开关关掉时**直接返回、不建任何动画** ——
语义一致：不是为了"看起来没动"，而是为了真的省掉开销。

**淡入**：1.0.0 需要给每张卡片挂 `QGraphicsOpacityEffect`（离屏合成，真正贵的地方），
所以它单独有一档开关；WPF 的 `Opacity` 动画是合成线程做的，便宜得多，
但开关照样生效（语义一致）。

**淡入的时长**（2.0 **有意**跟 1.0.0 不同）：1.0.0 的非 PCL 形态**压根不淡入**
（`SlideInRow` 给每种形态都建了 `QGraphicsOpacityEffect`，但只有 `_build_pcl()` 往它挂了动画）。
2.0 从第一版起就是"所有形态都淡入"，而且是"时长 = 整条轨迹、曲线 = 该档自己的缓动"——
那等于让透明度跟位移共用一条曲线，后果量出来很难看（缓出曲线在前 10% 就把透明度推到
0.27~0.65，淡入形同虚设；`back` / `elastic` 那两条更会让透明度冲到 1.25 再"淡"完）。
这一轮加了 `AnimationPreset.FadeRatio`（占整条轨迹的比例，默认 1.0 = 旧行为），
七档各自按"淡入到 0.9 比视觉落位早 60~150ms"扫出取值。

## 7. 不可能一样的地方（不是偷懒，是平台差异）
| 1.0.0 | 2.0 的处理 |
| --- | --- |
| QSS 的 `border-radius` 支持任意控件 | WPF 只有 `Border` / `ControlTemplate` 里能做圆角，所以每个控件都要写模板 |
| QSS 的 `:hover` / `:pressed` / `:checked` 伪状态 | 换成 `Trigger`（`IsMouseOver` / `IsPressed` / `IsChecked`） |
| `@变量@` 文本替换 | 运行时的 `DynamicResource` 查找（换主题不用重建控件） |
| `QGraphicsOpacityEffect` 离屏合成 | `UIElement.Opacity` 动画（合成线程） |
| Qt 的 `QPropertyAnimation` + 手算曲线 | `DoubleAnimation` + `IEasingFunction` |
| 「跟随系统深色」读 Qt 的 `colorScheme` | 读注册表 `AppsUseLightTheme`（读不到就当深色，跟 1.0.0 一致） |
| 字体 `"Segoe UI", "Microsoft YaHei UI", …` | 同一个字体族串，放在 `App.xaml` 的 `UiFont` |
| 布局的 `addSpacing(n)` | 见下面那条"间距" |

### 两条核对时踩到的、别的项目也会踩的坑

**① Qt 的 `addSpacing(n)` 不是"两边各加 spacing"。**
`setSpacing(10)` + `addSpacing(4)` 的实际间距是 **14**，不是 `10+4+10=24`
—— `QBoxLayout` 只在相邻两项之间插一次 spacing，显式那个间隔项顶掉了一侧。
启动面板第一版按 24 摆，总高 289；按 14 改完是 **270**，而 1.0.0 的截图量出来是 **269**。

**② 量参考截图要先定比例。**
1.0.0 的截图是 1280×820 的**客户端区**，但 `01-launch.png` 被缩过。用侧边栏
`setFixedWidth(224)` 在图里量到 184px 定出比例 0.8214，再往回换算面板尺寸：
高 `(810-589)/0.8214 ≈ 269`、宽 `(1269-895)/0.8214 ≈ 455`。
2.0 侧是独立量出来的 270 / 460 —— 两套排版引擎对上了，这个数就可信。

启动面板逐项实测（逻辑像素，相对卡片顶）：

| 元素 | 1.0.0（从截图量） | 2.0（渲染后量） |
| --- | --- | --- |
| 启动按钮顶 | 19.5 | 21 |
